camera, SDK library, SteamVR runtime, display or Frame was involved: the
frames are the fake backend's synthetic gradients served through memfd
descriptors, so every detection below is a label on a gradient and means
nothing about any object. This record establishes that the chain fits; the
device steps S4, S5, S8 and S9 remain the proof of concept itself.

   helper built (`--describe`: `build_commit` `544f8ac`, `build_dirty` false,

2. `scripts/camera_recognize.py --allow-camera-input --helper <the fake>
   --seconds 6 --max-frames 20 --fps 5 --cameras 0 --detector mobilenet-ssd
   --report <file> --helper-arg=--fake-scenario --helper-arg=export_nv12`,
   under `.venv-replay` (Python 3.12.3, OpenCV 4.12.0, ONNX Runtime 1.31.0,
   NumPy 2.2.6), with `XDG_RUNTIME_DIR` a fresh 0700 directory and stdin a
   pseudo-terminal: the command printed the export notice and its bounds and
   waited; a driver typed `yes`; only then did the helper start, with
   `--parent-confirmed`.
3. A first run with the fake's default scenario (metadata-only frame sets,
   no buffer descriptor) ended at once with the helper's `pixel_path_error`,
   detail `camera_0:buffer_descriptor_missing`, helper exit 1: the command
   reported `helper_ended_early`, the stream `complete` (one `ready`, one
   `end`), and no frame was processed. That is the intended refusal path, not
   a defect; the exporting scenario was then named.

## Limits

A cloud check against the fake backend: it proves the wire protocol, the
confirmation hand-off, the supervision, the strict reader and the command's
bounded loop agree on one machine. It proves nothing about the Arcturus
camera service, the real DMA-BUF modifiers (linear or UBWC), the Adreno
Vulkan import, passthrough, timings on the Frame, or recognition of any real
object; the fake's frames are gradients and the `tvmonitor` label is noise.
`sdk_release` is null because no SDK build was made. A second exporting run
with `--helper-arg=--pixel-path --helper-arg=gpu_convert` (12:58 UTC) took the
Vulkan path on the software driver (`llvmpipe`, LLVM 20.1.2, API 1.4.318,
import `linear_copy_fallback` because the software driver lacks the DRM
modifier extension; `frames_imported` 20): the same 20 frames exported and
processed, exit 0, inference p95 34.5 ms, 19 of 20 frames labelled. The real
DMA-BUF import by modifier, which the Frame's driver would take, is the part
no cloud run can reach. Nothing in this record is a device
result or an approval; the device steps follow the
[probe guide](../guides/camera-probe.md) and the
[recognition guide](../guides/camera-recognize.md) under the owner's separate
approvals (S4 is approved and waits for the owner's prerequisites on the Frame).
